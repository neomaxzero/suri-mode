# Reflect

When explicitly requested, examine the working approach and propose improvements the user can judge. A retrospective is not permission to edit skills or create tickets.

## Review the relevant evidence

- Establish the task or conversation in scope. Use available context and existing decision records first; retrieve additional history only for a material gap. Do not assume transcript access or search unrelated conversations.
- Focus on consequential decisions, user corrections, repeated friction, and approaches that failed or worked for a verifiable reason. Skip routine actions and do not classify every correction as a reusable lesson.
- Separate observations from interpretations. Support proposed changes with a concrete incident or recorded pattern, and state uncertainty where the evidence is incomplete.
- Work directly by default. Do not require multiple reviewers or a separate synthesizer; follow Suri's proportional model policy only when an independent check has concrete value.

## Propose a small set of changes

- Present only improvements that materially change future decisions or reduce demonstrated friction. For each, state the evidence, proposed adjustment, intended benefit, and relevant tradeoff.
- Check whether existing guidance already covers the issue. Distinguish missing instructions from failure to follow an existing rule; duplicating the rule is not automatically a fix.
- Distinguish repository-specific lessons, general working preferences, and objectively enforceable controls. Reuse the existing lesson and structural-prevention policies rather than inventing another memory or backlog system.
- Do not promise time or token savings without measurements. A successful outcome alone does not establish that the process was efficient or generally reusable.

## Preserve the decision boundary

- Leave product code, skills, and configuration unchanged during the retrospective. Do not create tickets, publish records, schedule reviews, or file backlog items automatically.
- Present the proposed subset and wait for explicit approval before applying it. An explicit request that already names a concrete change can authorize that change; approval of one proposal does not authorize the rest.
- If approved, use the relevant authoring workflow and verify the bounded edit. Preserve unrelated changes and existing human checkpoints.
- A finding of no justified changes is valid. Do not manufacture improvements to make the retrospective appear productive.

Keep the response brief: what happened, what should change and why, and any decision needed from the user. Retain evidence references without copying the transcript.
